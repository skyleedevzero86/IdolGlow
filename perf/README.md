## 폴더 구성

```text
perf/
├── k6/
│   ├── products-list.js            상품 목록 GET /products 를 반복 호출
│   ├── run-products-list.ps1       상품 목록 측정을 순서대로 실행
│   ├── reserve-contention.js       같은 슬롯이나 여러 슬롯에 예약을 동시에 보냄
│   └── run-reserve-contention.ps1  예약 측정을 순서대로 실행
├── sql/
│   ├── seed-products.sql           측정 전용 DB 에 상품 n 개와 찜·리뷰·슬롯을 만듦
│   └── explain-products.sql        상품 목록 SQL 의 실행 계획을 봄
└── results/
    ├── 2026-11-22/                 0.22.0 숫자의 원본 결과 파일 21개
    └── 2026-11-23-explain/         상품 4개, 1만 개, 5만 개 실행 계획
```

저장소 맨 위의 `k6-products.js`, `k6-reserve.js` 는 예전 기본판입니다. <br/>실제 측정은 이 폴더의 스크립트로 했습니다.

## 다시 측정하는 방법

### 준비

1. backend 폴더에서 `.\gradlew.bat bootRun` 으로 서버를 띄웁니다.
2. k6 를 설치합니다. 설치 안내는 https://k6.io 에 있습니다.

### 상품 목록 측정

```powershell
cd perf\k6
.\run-products-list.ps1 -Label after
```

- 예열 15초를 먼저 하고, 사용자 10명, 100명, 300명, 500명을 30초씩 따로 돌립니다.
- 결과는 `perf/results/날짜-after/` 폴더에 사용자 수별 파일로 저장됩니다.
- 같은 폴더의 `conditions.txt` 에 측정한 커밋 번호가 남습니다.
- 수정 전과 비교하려면 비교할 커밋으로 서버를 다시 띄우고 `-Label before` 로 한 번 더 돌립니다.

### 예약 경합 측정

예약 슬롯은 **시작 7일 전부터** 열립니다. <br/>그래서 시작일이 1일 뒤에서 6일 뒤 사이이고, 아직 예약되지 않은 슬롯이 필요합니다.
한 번 돌리면 슬롯이 예약되므로, 수정 전과 수정 후에는 **각각 새 슬롯**을 쓰거나 측정 뒤 슬롯을 비워야 합니다.

```powershell
$env:TOKEN = "로그인 토큰"
cd perf\k6
.\run-reserve-contention.ps1 -Label after -WarmupSlot 133 -BurstSlot 92 -SpreadFrom 93
```

스크립트는 아래 네 단계를 순서대로 돌립니다.

| 단계       | 요청             | 대상 슬롯                   | 기대하는 결과                                    |
| ---------- | ---------------- | --------------------------- | ------------------------------------------------ |
| 1. 예열    | 초당 50건, 15초  | 이미 예약된 슬롯 1개        | 모두 거절. 서버를 데우는 단계라 비교에 쓰지 않음 |
| 2. 몰림    | 100명 동시       | 슬롯 1개                    | 성공 1건, 거절 99건                              |
| 3. 오픈    | 300명 동시       | 슬롯 30개에 흩어짐          | 성공 30건, 거절 270건                            |
| 4. 매진 뒤 | 초당 100건, 15초 | 3단계에서 다 팔린 슬롯 30개 | 모두 거절                                        |

참고할 점

- 상품 번호나 가격이 다르면 `$env:PRODUCT_ID`, `$env:TOTAL_PRICE` 로 바꿉니다.
- 로그인 토큰은 결과 파일에 남지 않습니다.<br/> 측정이 끝나면 스크립트가 `$env:TOKEN` 도 지웁니다.
- 측정 뒤에는 DB 에서 슬롯마다 예약이 1건 이하인지 직접 세어 초과 예약이 없는지 확인합니다.

## 2026-11-22 자세한 결과

### 상품 목록, 단계마다 30초

| 사용자 | 수정 전 처리량 | 수정 전 p95 | 수정 후 처리량 | 수정 후 p95 | 실패율 변화 |
| -----: | -------------: | ----------: | -------------: | ----------: | ----------- |
|   10명 |   초당 206.7건 |     108.0ms |   초당 269.2건 |      86.2ms | 0% → 0%     |
|  100명 |    초당 92.9건 |   2,548.7ms |   초당 338.7건 |     566.6ms | 0% → 0%     |
|  300명 |   초당 173.5건 |   2,934.8ms |   초당 311.7건 |   1,573.2ms | 3.43% → 0%  |
|  500명 |   초당 120.9건 |   7,794.1ms |   초당 346.8건 |   2,261.1ms | 0% → 1.51%  |

- 수정 전에는 100명일 때 처리량이 10명일 때보다 오히려 줄었습니다.
- 원인은 커넥션 풀이었습니다. <br/>같은 시간에 풀 10개가 모두 사용 중이었고 91개 요청이 기다렸는데, DB CPU 는 0.16% 였습니다. 이때의 결과가 `products-before-100-poolcheck.json` 입니다.
- 수정 후에도 500명에서는 실패가 1.51% 나왔습니다.<br/> 커넥션 풀 10개와 한 대의 PC 라는 조건의 한계로 보고 아직 따로 고치지 않았습니다.

| 오픈, 300명 → 슬롯 30개  |   1,156.4ms |     694.3ms | 두 버전 모두 성공 30, 거절 270 |

## 2026-11-23 데이터를 늘린 실행 계획

상품을 4개에서 1만 개, 5만 개로 늘리고 상품 목록 SQL 의 실행 계획을 봤습니다. <br/>
개발 DB 는 건드리지 않고, 같은 컨테이너 안에 측정 전용 DB `idolglow_perf` 를 따로 만들어 썼습니다.

### 만든 데이터

| 상품 수 | 회원 |    찜 | 리뷰 | 태그 | 예약 슬롯 |
| ------: | ---: | ----: | ---: | ---: | --------: |
|     1만 |  2만 |  30만 | 10만 |  3만 |      10만 |
|     5만 | 10만 | 150만 | 50만 | 15만 |      50만 |

### 결과, SQL 한 번의 실행 시간

| SQL                          | 상품 4개 | 상품 1만 개 | 상품 5만 개 |
| ---------------------------- | -------: | ----------: | ----------: |
| 기본 정렬, 최신순            |   0.04ms |      0.04ms |      0.12ms |
| **인기순 정렬**              |    1.3ms | **1,295ms** | **5,289ms** |
| 키워드, 걸리는 상품이 많음   |    3.4ms |        23ms |       166ms |
| **키워드, 걸리는 상품 없음** |   0.07ms |    **62ms** |   **333ms** |
| 찜 수, 20개 상품             |   0.05ms |       3.0ms |       7.5ms |
| 20개 상품 내용 채우기        |    1.7ms |       0.5ms |       0.6ms |

- 기본 정렬과 20개 상품 내용 채우기는 데이터가 늘어도 거의 그대로입니다. <br/> 0.22.0 에서 고친 N+1 쿼리도 이 부분이라, 데이터 크기와 상관없이 빠르게 유지됩니다.
- **인기순 정렬**은 상품 수에 비례해 느려집니다. <br/> 화면에는 20개만 보이는데, 모든 상품마다 찜 수, 평균 별점, 리뷰 수를 구하는 하위 쿼리를 3개씩 돌린 뒤 전체를 정렬하기 때문입니다. <br/> 1만 개일 때 하위 쿼리가 3만 번 돌고 메모리 블록을 26만 번 읽었습니다.
- **키워드 검색**은 `LIKE '%검색어%'` 라서 인덱스를 쓰지 못하고 상품과 태그를 모두 훑습니다. <br/> 걸리는 상품이 없을 때가 가장 느립니다.
- 아직 고치지 않았습니다. 고치는 방법은 아래 두 가지를 검토 중입니다.
  - 인기순: 찜 수, 평균 별점, 리뷰 수를 미리 모아 둔 칸이나 표를 두고 인덱스로 정렬
  - 키워드: pg_trgm 같은 부분 문자열 인덱스

### 다시 보는 방법

```powershell
docker exec idolglow-postgres sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "create database idolglow_perf"'
```

1. 위 명령으로 측정 전용 DB 를 만들고, `backend/src/main/resources/db/migration/postgres` 의 ps1 부터 ps7 까지를 순서대로 넣습니다.
2. `perf/sql/seed-products.sql` 을 `-v n=10000` 처럼 상품 수를 정해 실행합니다. <br/>1만 개는 약 45초 걸립니다.
3. `perf/sql/explain-products.sql` 을 실행하면 SQL 마다 실행 시간과 읽은 블록 수가 나옵니다.

결과 파일은 `results/2026-11-23-explain/` 에 상품 수별로 있습니다.
